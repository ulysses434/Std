Мультиоблачная архитектура для сервиса "Сосисочная"

1. Плюсы решения:
- Высокая отказоустойчивость: при выходе из строя AWS (основной кластер), 
  GCP автоматически принимает трафик через Global Load Balancer, и заказы 
  продолжают обрабатываться.
- Географическая распределенность: клиенты подключаются к ближайшему 
  облаку (AWS для Европы, GCP для Азии), что снижает задержки (пинг).
- Избежание вендор-лока: возможность гибко переносить сервисы между 
  провайдерами при изменении тарифов.
- Единое хранилище изображений в Yandex Cloud: экономия на хранении и 
  доставке контента через S3 API.

2. Минусы и ограничения:
- Сложность синхронизации данных: между PostgreSQL и MongoDB идет 
  асинхронная репликация. Клиент может увидеть заказ в AWS, но не сразу 
  в GCP (работаем с eventual consistency).
- Высокие затраты на межоблачной трафик: репликация БД и VPN-туннель 
  генерируют большой объем данных, что увеличивает бюджет.
- Усложнение дебага: при ошибке заказа нужно проверять логи в двух 
  облаках, что замедляет расследование инцидентов.

3. Особенности архитектуры:
- Приоритетная обработка: через Global Load Balancer основной трафик 
  (оформление заказов) идет в AWS EKS, а тяжелые фоновые задачи (отчеты, 
  расчет доставки) вынесены в GKE, чтобы не перегружать критический путь.
- Кэширование каталога: MongoDB Atlas в GCP используется как read-replica 
  для быстрой выдачи клиентам каталога сосисок без обращения к основному 
  кластеру.
- Безопасность: Vault централизованно хранит ключи от платежных систем 
  (YooKassa, Stripe) и синхронизируется между облаками через VPN-туннель.
- CI/CD деплоит сразу в оба кластера, что гарантирует одинаковую версию 
  микросервисов в обеих зонах (используется Blue/Green стратегия).
